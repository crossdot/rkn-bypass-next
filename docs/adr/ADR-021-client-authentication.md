# ADR-021: Клиентская аутентификация (mTLS per-client)

## Статус: Принято

## Контекст
Сейчас любой, кто имеет `dev-ca.crt`, подключается к серверу. Нет per-client
идентификатора, отзыва, лимита активных сессий, ротации ключей. Это нарушает
требование «у каждого клиента собственный идентификатор и отдельный секрет»
(P2.2) и блокирует P4/P5: добавлять транспорты без аутентификации — значит
наращивать поверхность атаки.

## Решение
1. **mTLS** с per-client сертификатами X.509. Клиент предъявляет собственный
   сертификат в TLS-handshake; сервер проверяет его через
   `WebPkiClientVerifier` + кастомный deny-list.
2. **Идентичность клиента** — fingerprint = SHA-256 от **DER-encoded**
   сертификата (не PEM), hex-encoded. `client_id` — человекочитаемое имя,
   привязывается к fingerprint в конфиге; в логах `client_id` не пишется
   открыто — только SHA-256 (усечённый до 12 hex).
3. **Отказ — на TLS-уровне** (в `ClientCertVerifier`), до `ConnectAck`.
   Неизвестный или отозванный клиент не доходит до прикладного слоя.
4. **Отзыв** — deny-list по fingerprint (`revoked`). **Ротация** — новый
   сертификат + старый fingerprint в deny-list (не «продление срока»).
5. **`max_sessions`** — отдельный механизм (session manager) после
   TLS-handshake, не часть TLS-аутентификации.
6. **`key_material`** — путь к PEM-файлу **публичного** сертификата клиента
   (на сервере); приватный ключ — только у клиента и в него не попадает.
7. **admin-cli**: `add` генерирует ключ + сертификат, подписанный
   существующим CA; приватный ключ выводится только в stdout, не логируется,
   не попадает в `Debug`/`Display`.
8. **Криптография** — только проверенные библиотеки: rustls (mTLS), rcgen
   (выпуск сертификатов), ring (SHA-256). Собственной криптографии нет.

## Альтернативы
- **PSK**: rustls 0.23 без first-class PSK → кастомный challenge-response
  (свой протокол). Отклонено.
- **Подписанные токены**: самодельный протокол + отказ уже после
  TLS-handshake. Отклонено.

## Модель угроз
- **Скомпрометированный клиент**: отзыв по fingerprint; остальные клиенты
  не затронуты.
- **Отзыв**: deny-list fingerprint, применяется после перезагрузки конфига.
- **Ротация**: новый сертификат; старый fingerprint в deny-list.
- **Брутфорс**: приватные ключи (ECDSA P-256) не перебираются; сертификат
  подписан CA — подделать без CA нельзя.
- **Компрометация CA**: затрагивает всех клиентов; ротация CA — вне MVP.

## Границы crypto
- Не реализуем свою криптографию: только rustls (TLS/mTLS), rcgen
  (выпуск сертификатов), ring (SHA-256).
- Секреты не реализуют `Debug`/`Display`/`Error`, не попадают в логи,
  ошибки, panic-сообщения.

## Что не делаем
- CRL/OCSP, короткоживущие сертификаты, автоматическая ротация CA.
- Сетевое администрирование: admin-cli работает только локально.

## Последствия
- Новый крейт `crypto`, per-client конфиг в `config`, `apps/admin-cli`.
- Сервер требует mTLS; без валидного сертификата — отказ на TLS-уровне.
- Docker smoke: без ключа — отказ, с ключом — HTTP 200.

## Отзыв и ротация
- Отзыв/ротация применяются после перезагрузки конфига сервером.
- Живой reload — Phase 2 (отдельный ADR).
- Существующие сессии отозванного клиента разрываются при перезапуске
  сервера (TCP-соединения закрываются).
- В multi-server конфигурации отзыв нужно применить на каждом сервере.
- Проверка идентичности конфига на N серверах: INFO-строка `config_hash`
  при старте. Совпадение хешей = одинаковая конфигурация fingerprints.
- Проверено тестом `tests/mtls_revoke.rs`: отозванный клиент не
  устанавливает новое соединение после рестарта с обновлённым конфигом.

## Логи и секреты
- `ConfigError` не содержит содержимого конфига: только путь, line/column
  и текст ошибки парсера.
- Inline PEM (клиентские ключи) не попадает в `Display`/`Debug` ошибок
  конфигурации.
- Проверено для toml 0.5.11. При апгрейде toml перепроверить, что
  Display/source() не содержат исходного текста конфига.
