# ADR-019: Оптимистичный SOCKS5 REP_SUCCESS в MVP

## Статус: Superseded (замещён реализацией ack-протокола)

## Контекст
В MVP клиент отправляет SOCKS5 REP_SUCCESS сразу после установления
TLS-соединения с сервером, не дожидаясь подтверждения соединения
с целевым адресом. Это упрощает протокол, но приводит к ложным
успехам: если цель недоступна, клиент узнаёт об этом только
по обрыву соединения.

## Решение
1. В MVP оптимистичный REP_SUCCESS допускается как временное решение.
2. Это поведение **не считается production-ready**. Оно нарушает
   требование «клиент не сообщает об успехе, которого фактически нет»
   (docs/requirements.md).
3. Следующий спринт вводит ack-протокол: сервер подтверждает
   успешный `TcpStream::connect` к цели; клиент отправляет
   REP_SUCCESS только после ack.
4. До введения ack-протокола оптимистичный REP_SUCCESS
   документируется в README и в сообщениях об ошибках клиента.

## Последствия
- Один лишний round-trip после введения ack-протокола.
- Тесты на «цель недоступна» должны проверять, что клиент получает
  ошибку, а не «успех с последующим обрывом».
- Оптимистичный REP_SUCCESS нельзя переносить в Phase 2 или
  production без явного пересмотра этого ADR.
